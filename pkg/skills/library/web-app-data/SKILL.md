# Web App with Data Starter — Stack Knowledge

This project is the **`web-app-data` starter**: the client-side React app from
the `web-app` starter **plus a data layer**. One Cloudflare **Worker** serves
both halves — the built app from `dist/` as static assets and a **Hono** JSON
API under `/api/*` — and the API reads and writes a Cloudflare **D1** database
(SQLite) through **Drizzle ORM**. App and data share one origin, one dev
server and one deploy.

Read the `web-app` skill for the client half (router, hooks, components); this
skill covers the data half and how the two fit together.

Commands come from `.sprout/starter.json` — never guess them:

```json
{ "build": "npm run build", "test": "npm test",
  "dev": "npm run dev", "format": "npm run format", "lint": "npm run lint" }
```

`npm run build` type-checks the app **and the worker** (`tsc --noEmit`) then
builds the app into `dist/`; `npm run dev` is `wrangler dev` (port 8787);
`npm test` runs the UI suite and then the Worker API suite (see the two-config
vitest split).

## Layout — where things go

```
src/
  main.tsx              entry point; mounts <App/> into #root
  App.tsx               the React Router route table (/, /about, /items)
  layouts/Layout.tsx    the shared shell rendered around every route
  pages/                one component per route; Items.tsx calls the API
  hooks/useLocalStorage.ts  client-side persisted state
  worker/
    index.ts            THE API: the Hono app, its routes, exported as the Worker default
    schema.ts           THE schema: Drizzle table definitions (sqlite-core)
drizzle/
  migrations/           SQL migrations wrangler d1 migrations applies
    0000_init.sql       creates `items`
    meta/_journal.json  drizzle-kit's migration index
drizzle.config.ts       drizzle-kit config: schema path + migrations output dir
wrangler.toml           Worker + bindings: [assets], [[d1_databases]], commented KV/R2
test/
  app.test.tsx          UI test (jsdom, in-memory router, stubbed fetch)
  api.test.ts           API test (Workers runtime, local D1)
vitest.config.ts        UI test config (jsdom)
vitest.workers.config.ts  API test config (Workers pool, D1 binding)
public/                 copied into dist/ (favicon, _redirects)
dist/                   build output (gitignored); never edit by hand
```

Rules of thumb:

- **API routes live in `src/worker/index.ts`.** It is one Hono app
  (`const app = new Hono<{ Bindings: Env }>()`) with `app.get(...)` /
  `app.post(...)` handlers keyed by path, exported as
  `export default app`. Add a route by adding a handler there.
- **The schema lives in `src/worker/schema.ts`**, built with
  `drizzle-orm/sqlite-core` (D1 is SQLite). Each table is a `sqliteTable(...)`
  export; the inferred row types come from `$inferSelect` / `$inferInsert`.
- **Migrations live in `drizzle/migrations/`** as numbered `.sql` files.
  `wrangler d1 migrations apply` runs them in order; `0000_init.sql` is the
  first.
- **The client lives in `src/pages/` and `src/App.tsx`** (React Router), the
  same as the plain `web-app` starter. The page that talks to the API is
  `src/pages/Items.tsx`.
- **Bindings are declared in `wrangler.toml`** and typed in the `Env` type in
  `src/worker/index.ts`. The handlers read them from `c.env` — never from a
  global.
- **Never edit `dist/`** — it is regenerated by `npm run build`.

## The API and its bindings

`src/worker/index.ts` declares the environment and wires D1 into Drizzle per
request:

```ts
export type Env = {
  DB: D1Database;
  ASSETS: Fetcher;
};

const app = new Hono<{ Bindings: Env }>();

app.get('/api/items', async (c) => {
  const db = drizzle(c.env.DB);
  const rows = await db.select().from(items).orderBy(asc(items.id));
  return c.json(rows);
});
```

Key points, which you must match:

- **`Env` is the contract** between `wrangler.toml` and the code. Every binding
  a handler uses must appear in it; a binding present in `wrangler.toml` but
  missing from `Env` is invisible to the handler (and a `c.env.X` that is not
  in `Env` is a TypeScript error).
- **`drizzle(c.env.DB)` per request**, not at module scope. The binding is
  only valid inside a request (or during a test); a module-scope `drizzle`
  capture races across requests.
- **Handlers return `c.json(...)`** with an explicit status (`200` by default,
  `201` on create, `400` for a bad body).
- **Validate the request body in a helper** (the starter's `readName`), and
  return a typed error shape (`{ error: '...' }`) with a 4xx status — do not
  throw into the Worker's default error path.
- The **assets binding (`ASSETS`) is declared for type completeness only**:
  the Worker runtime serves `dist/` before the Hono app sees a request, so no
  handler reads it.
- API paths are **relative and under `/api/`** (`/api/items`). The client
  fetches `/api/items` — same origin in dev and in production.

## Adding a table, end to end

Adding a table is **five steps** — four coordinated edits plus a test; skipping
any one leaves the app broken in a way that passes the build.

**1. Add the table to the Drizzle schema.** Append a `sqliteTable` to
`src/worker/schema.ts`:

```ts
import { integer, sqliteTable, text } from 'drizzle-orm/sqlite-core';

export const notes = sqliteTable('notes', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  body: text('body').notNull(),
});
```

**2. Generate the migration.** `npx drizzle-kit generate` reads
`drizzle.config.ts` (schema at `src/worker/schema.ts`, output to
`drizzle/migrations/`) and writes the next numbered `.sql` next to
`0000_init.sql` (e.g. `0001_<name>.sql`) plus a `meta/_journal.json` entry. If
you cannot run drizzle-kit, hand-write the `.sql` **and** add its journal
entry, matching the style of `0000_init.sql`. Never edit `0000_init.sql` to
add a table — migrations are append-only history.

**3. Apply it locally.** `npm run db:migrate`
(`wrangler d1 migrations apply web-app-data-db --local`) applies the pending
migrations to the local D1 under `.wrangler/state/`. Until you do this the
route is broken locally even though the schema file is correct.

**4. Add the API route** in `src/worker/index.ts` (import the table, add a
handler), and call it from the client in `src/pages/Items.tsx` or a new page
registered in `src/App.tsx`.

**5. Add a test.** Extend `test/api.test.ts`: apply the new migration into
the test database (the same split-on-`;` helper), then exercise the route
through `SELF.fetch`. For a new UI page, add a case to `test/app.test.tsx`
with a stubbed `fetch`, or a new spec under `test/`.

**Deploying:** replace the `database_id` placeholder in `wrangler.toml` with
the id `wrangler d1 create web-app-data-db` prints, run
`npm run db:migrate:remote` to apply migrations to the remote database, then
deploy. The manifest declares `deploy_target: workers`.

## Local vs deployed bindings

- **`wrangler.toml` is the single source of bindings**, read by `wrangler dev`,
  `wrangler deploy` and the test pool.
- **The D1 binding is `DB`** (`[[d1_databases]]`, `database_name =
  "web-app-data-db"`, `migrations_dir = "drizzle/migrations"`).
- **Locally there is no Cloudflare account.** `wrangler dev` (and the test
  pool) emulate D1 with local state under **`.wrangler/state/`**, keyed by the
  database name — **not** by `database_id`. So the placeholder
  `database_id = "00000000-..."` works for local development and tests; you
  replace it only at deploy time with the real id.
- **`compatibility_date` and `compatibility_flags = ["nodejs_compat"]`** are
  set in `wrangler.toml`; `nodejs_compat` is required by the
  `@cloudflare/vitest-pool-workers` pool (and harmless in production).
- **KV and R2 are documented but NOT wired.** `wrangler.toml` carries
  commented `[[kv_namespaces]]` and `[[r2_buckets]]` blocks; nothing binds
  them by default. To use one, create the namespace/bucket, uncomment its
  block (filling in the real id/name), add the binding to `Env` in
  `src/worker/index.ts` (`KV: KVNamespace`, `BUCKET: R2Bucket`), and read it
  from `c.env`. Local dev and tests then emulate it in `.wrangler/state/`
  automatically. Do not add a binding nothing uses — dead config.

## The two-config vitest split

`npm test` runs **two** vitest runs because one config cannot serve both
environments:

- **`vitest.config.ts`** — UI tests under **jsdom** with Testing Library.
  `include: ['test/**/*.test.{ts,tsx}']`, `exclude: ['test/api.test.ts',
  'node_modules/**']`.
- **`vitest.workers.config.ts`** — the API test **inside the Workers runtime**
  (`defineWorkersConfig` from `@cloudflare/vitest-pool-workers`), reading
  `wrangler.toml` for bindings and local D1. `include: ['test/api.test.ts']`.

A new **UI** spec goes under `test/` and is picked up by the jsdom config
automatically. A new **API** spec must match `vitest.workers.config.ts`'s
`include` — either extend `test/api.test.ts` or add a pattern there; a spec
placed under `test/*.test.ts` that needs the Workers runtime but is not
excluded from `vitest.config.ts` will be run by jsdom and fail on
`cloudflare:test`. Keep the exclusion and include lists consistent when you
add files.

## Patterns to use

- **Add a table in the schema, then a migration, then apply it, then the
  route** — in that order; each step depends on the last.
- **Compute derived columns in SQL** (`asc(items.id)`, a `where`, a `limit`)
  rather than fetching everything and filtering in JS.
- **Type rows from the schema** with `$inferSelect` / `$inferInsert` so the
  API and the client agree on shape.
- **Validate input in a small helper** and return `{ error }` with a 4xx.
- **Apply migrations in `beforeAll` of an API test** so each suite runs
  against a known schema.
- **Read bindings from `c.env`**, declared in `Env` and `wrangler.toml`.

## Patterns to avoid

- **Do not use Node-only APIs in the Worker.** `fs`, `path`, `process`,
  `Buffer`-heavy libraries and anything touching the filesystem are not
  available in the Workers runtime unless `nodejs_compat` explicitly supports
  them. Use Web APIs (`fetch`, `Request`/`Response`, `crypto`, `URL`) and the
  binding APIs (`D1Database`, `KVNamespace`, `R2Bucket`). Worker code runs in
  an isolate, not Node.
- **Do not import the D1/Worker modules into client code.** `src/worker/*`
  uses `drizzle-orm/d1`, the `Env` bindings and `cloudflare:test`-adjacent
  types that only exist in the Worker runtime. The client must reach the data
  **only** through `fetch('/api/...')`.
- **Do not create the Drizzle client at module scope** — build it per request
  from `c.env.DB`.
- **Do not hardcode `database_id` or any secret** in code. The placeholder is
  replaced at deploy; secrets belong in `wrangler secret put` bindings, read
  from `c.env`, never committed.
- **Do not assume a schema change is live after editing `schema.ts`.** The
  database only changes when a migration is applied.
- **Do not edit `dist/` or `0000_init.sql`.**

## Known failure modes for open models

These are the mistakes that recur on this stack — check for them before
declaring a change done:

1. **Node-only APIs in the Worker.** Reaching for `node:fs`, `node:path`,
   `process.env`, or a Node-only npm package because the code "runs in
   JavaScript". The Workers runtime is not Node; those imports fail at
   runtime (or are stubbed to throw). Use the Web-platform APIs and the
   binding objects on `c.env`. `nodejs_compat` covers only a subset — do not
   treat it as full Node.
2. **Forgetting to apply the migration.** Editing `schema.ts` and adding a
   route, then calling it — the handler runs against a database that has no
   such table and every request 500s ("no such table"). Locally the fix is
   `npm run db:migrate`; deployed, `npm run db:migrate:remote`. A schema file
   without an applied migration is the single most common cause of "the route
   works in my head but fails at runtime".
3. **Secrets and ids hardcoded.** Putting an API token, a real `database_id`
   or a KV namespace id literally in `src/worker/index.ts` or committed into
   `wrangler.toml`. Secrets come from `wrangler secret put <NAME>` and are
   read from `c.env.<NAME>`; the placeholder `database_id` is replaced only
   at deploy time. Committing a token leaks it into git history.
4. **The two-config vitest split pitfall.** A new test written for the Worker
   runtime but placed where the **jsdom** config picks it up (or not excluded
   from it) fails on the `cloudflare:test` import, and a Workers-runtime test
   that is not matched by `vitest.workers.config.ts`'s `include` silently
   never runs. Conversely, a UI test left in the workers config runs without a
   DOM. Keep `include`/`exclude` consistent in both configs when adding specs.
5. **Client reaching past the API.** Importing `src/worker/schema.ts` (or
   `drizzle`) into a page and querying "directly" — the browser has no
   binding, no D1 and no Drizzle runtime. The client talks to the data only
   over `fetch('/api/...')`. Keeping the schema out of the client bundle also
   keeps it small.
6. **Mixing the plain `web-app` layout with this one.** This starter adds
   `src/worker/`, `drizzle/` and `wrangler.toml`. Do not assume the plain
   `web-app` starter's "there is no backend" rule here: there *is* an API, and
   it is the only path to persistent data. Statements like "no fetch on load"
   from the client-only skill do not apply — `Items.tsx` fetches on mount
   deliberately.
