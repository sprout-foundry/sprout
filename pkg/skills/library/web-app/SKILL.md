# Web App Starter — Stack Knowledge

This project is a **React single-page app** (the `web-app` starter): React 18
rendered by Vite into a static bundle in `dist/`, routed client-side by
**React Router 7** (`react-router-dom`). All rendering happens in the browser —
there is no server rendering and no backend. Work with that grain: state lives
in components and hooks, navigation happens through the router, and the host
just serves `index.html` for every path.

Commands come from `.sprout/starter.json` — never guess them:

```json
{ "build": "npm run build", "test": "npm test",
  "dev": "npm run dev", "format": "npm run format", "lint": "npm run lint" }
```

`npm run build` type-checks (`tsc --noEmit`) and bundles into `dist/`;
`npm test` runs vitest in jsdom with Testing Library.

## Layout — where things go

```
src/
  main.tsx           entry point; mounts <App/> into #root and imports global CSS
  App.tsx            THE router: the route table, wrapped in the shared layout
  layouts/
    Layout.tsx       the shared shell (header, nav, footer) rendered around every route
  pages/
    Home.tsx         the '/' route (index route)
    About.tsx        the '/about' route (child route)
  hooks/
    useLocalStorage.ts  the persisted-state hook the pages compose
  styles/
    global.css       global CSS, imported once by main.tsx
public/              copied verbatim into dist/ (favicon.svg, _redirects)
test/                vitest specs (*.test.tsx) + setup.ts
dist/                build output (gitignored); never edit by hand
```

Rules of thumb:

- **A route is an entry in the route table in `src/App.tsx`, plus a component
  under `src/pages/`.** Adding a page is two edits, not one — the component
  alone is unreachable.
- **Shared markup** (header, nav, footer) lives in `src/layouts/Layout.tsx`,
  which renders its children through `<Outlet />`. Pages are nested under it in
  the route table, so the shell renders once around every route.
- **Reusable UI** (a component used by more than one page, or one worth
  isolating) lives in `src/components/` and is imported where used.
- **Cross-cutting client state** that survives a reload belongs in a hook under
  `src/hooks/` — `useLocalStorage` is the one this starter ships.
- **Static files served as-is** (favicon, `_redirects`) go in `public/` and are
  referenced from the site root, e.g. `href="/favicon.svg"`.
- **Never edit `dist/`** — it is regenerated by `npm run build`.

## The router

`src/App.tsx` is the single source of routes. It uses the **data-router API**:

```tsx
import { createBrowserRouter, RouterProvider } from 'react-router-dom';
import Layout from './layouts/Layout';
import Home from './pages/Home';

const router = createBrowserRouter([
  {
    path: '/',
    element: <Layout />,
    children: [
      { index: true, element: <Home /> },
      { path: 'about', element: <About /> },
    ],
  },
]);

export default function App() {
  return <RouterProvider router={router} />;
}
```

Key points of THIS API, which the starter uses and you must match:

- `createBrowserRouter([...])` builds the router from a **route-object array**;
  `<RouterProvider router={router} />` renders it. The router is created once at
  module scope, not on every render.
- The layout is the **parent route** (`element: <Layout />`) and pages are its
  `children`. The layout renders `<Outlet />`, which is where the matched child
  renders.
- `{ index: true, element: <Home /> }` is the **index route** — it renders at
  the parent's own path (`/`). A child with `path: 'about'` renders at
  `/about`; child paths are **relative** (no leading slash).
- Links are `Link` / `NavLink` (from `react-router-dom`). `NavLink` adds an
  active class by default and is what the nav uses.

## Adding a route

Two edits:

1. Create `src/pages/<Name>.tsx` exporting a component:

   ```tsx
   import { Link } from 'react-router-dom';

   export default function Pricing() {
     return (
       <>
         <h1>Pricing</h1>
         <p>Content goes here.</p>
         <Link to="/">Back home</Link>
       </>
     );
   }
   ```

2. Add it to the `children` array in `src/App.tsx` (import it at the top,
   then add the entry):

   ```tsx
   import Pricing from './pages/Pricing';

   // ...inside the children array of the '/' route:
   { path: 'pricing', element: <Pricing /> },
   ```

If the page should appear in the nav, add a `<NavLink to="/pricing">Pricing</NavLink>`
list item in `src/layouts/Layout.tsx` so navigation stays consistent.

## Adding a component with state

For component-local state, use `useState`. For state that should survive a
reload, use the `useLocalStorage` hook (`src/hooks/useLocalStorage.ts`) rather
than reaching for `localStorage` directly:

```tsx
import { useState } from 'react';
import { useLocalStorage } from '../hooks/useLocalStorage';

export default function Counter() {
  const [count, setCount] = useLocalStorage('count', 0);
  const [step, setStep] = useState(1);

  return (
    <>
      <p data-testid="count">{count}</p>
      <button type="button" onClick={() => setCount(count + step)}>
        Add {step}
      </button>
    </>
  );
}
```

`useLocalStorage<T>(key, initial)` returns `[value, set]` as a const tuple. It
reads the stored value **lazily** on first render (a `useState` initializer, so
storage is never touched on every render), falls back to `initial` when the
stored value is missing or malformed, and writes through `JSON.stringify` on
every set. Because the value is JSON round-tripped, `T` must be
JSON-serializable — plain objects, arrays, numbers, strings, booleans. When a
plain component-local value is all you need, `useState` is correct; do not
persist everything.

### Styling conventions

The starter uses **plain CSS** (`src/styles/global.css`, plus any per-component
CSS you add). No CSS-in-JS library and no utility framework are configured.

### Lint config

`eslint.config.mjs` runs the standard rules plus `eslint-plugin-react-hooks`
(so `exhaustive-deps` and the rules-of-hooks are enforced) and
`eslint-plugin-react-refresh` (warns when a file exports both components and
non-components). `npm run lint` is a real gate — a hooks-rules violation fails
it, which is usually the right signal.

## Adding a test

Tests are vitest specs under `test/` with Testing Library, run in **jsdom**.
`test/setup.ts` installs the jest-dom matchers and clears the DOM and
`localStorage` after each test. Render a route with an **in-memory router**
(`createMemoryRouter`) so any path can be asserted directly — the pattern from
`test/app.test.tsx`:

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { createMemoryRouter, RouterProvider } from 'react-router-dom';
import { describe, expect, it } from 'vitest';
import Layout from '../src/layouts/Layout';
import Home from '../src/pages/Home';

function renderRoute(path: string) {
  const router = createMemoryRouter(
    [
      {
        path: '/',
        element: <Layout />,
        children: [
          { index: true, element: <Home /> },
          { path: 'about', element: <About /> },
        ],
      },
    ],
    { initialEntries: [path] },
  );
  return render(<RouterProvider router={router} />);
}

describe('home route', () => {
  it('renders the heading and persists the visit count', async () => {
    const user = userEvent.setup();
    renderRoute('/');
    expect(screen.getByRole('heading', { name: 'Welcome' })).toBeInTheDocument();
    expect(screen.getByTestId('visit-count')).toHaveTextContent('0');
    await user.click(screen.getByRole('button', { name: 'Add a visit' }));
    expect(localStorage.getItem('visits')).toBe('1');
  });
});
```

Conventions this starter follows:

- **Query by role, name, or test id** (`getByRole`, `getByLabelText`,
  `getByTestId`) — not by CSS class or DOM structure.
- **Drive interaction with `userEvent`** (`const user = userEvent.setup()` then
  `await user.click(...)`), not `fireEvent`; it exercises the real event path.
- **Duplicate the route table in the memory router**, with
  `initialEntries: [path]` to pick the route. Route *navigation* is not driven
  in tests (the data router navigates through `fetch`, which jsdom cannot
  serve) — assert each route by rendering it, and assert links via their
  `href`.
- Any spec under `test/**/*.test.tsx` is picked up automatically
  (`vitest.config.ts` `include`); nothing to register.

## Patterns to use

- **Create the router once at module scope** in `App.tsx` — never inside a
  component render, or a new router (and history) is built every render.
- **`<Outlet />` for layout composition**: nested routes render where the
  parent's `Outlet` sits.
- **Relative child paths** in the route table (`path: 'about'`, not `/about`).
- **`Link` / `NavLink` for in-app navigation** — they keep the SPA behaviour
  and history intact.
- **The `useLocalStorage` hook for persisted state**, and `useState` for
  component-local state.
- **Derive during render** when a value is a pure function of props/state — a
  plain `const` in the component body (or `useMemo` only if it is genuinely
  expensive).

## Patterns to avoid

- **Do not mix router APIs.** This starter uses the data router
  (`createBrowserRouter` + `<RouterProvider>`). Do **not** introduce
  `<BrowserRouter>` with `<Routes>`/`<Route>` alongside it, or `useRoutes`,
  or `createHashRouter` — a second router instance in the tree is a runtime
  error ("You cannot render a `<Router>` inside another `<Router>`") or an
  inert duplicate. Stay with the route-object array.
- **Do not add a server or a backend.** This is a client-only SPA; a `fetch`
  on load expects an API the starter does not ship. Handle submission against
  an endpoint you configure explicitly, not an assumed one.
- **Do not put per-route chrome in pages.** Header/nav/footer belong in
  `Layout`; pages render only their own content.
- **Do not use `useEffect` to compute a value from props or state.** Derive it
  during render instead (see failure mode 2).
- **Do not read/write `localStorage` directly in components.** Use
  `useLocalStorage`, which handles the JSON round-trip and the malformed-value
  fallback.
- **Do not edit `dist/` or commit it.**

## Known failure modes for open models

These are the mistakes that recur on this stack — check for them before
declaring a change done:

1. **Stale closures in effects.** An effect (or an interval/timeout/event
   handler) registered once captures the props/state values from the render in
   which it was created, so it keeps reading the *old* value. The classic
   symptom is a counter that only ever reaches 1, or a handler that logs the
   initial state forever. Fix by listing every value the effect reads in its
   dependency array (the `react-hooks/exhaustive-deps` lint rule flags a
   missing one — heed it), or by using a functional update
   (`setCount((c) => c + 1)`) so the setter reads the latest value instead of
   the captured one. Do not silence the lint rule with an empty `[]` "to run it
   once".
2. **`useEffect` used for derived state.** Writing
   `useEffect(() => setFullName(first + ' ' + last), [first, last])` to compute
   a value from other state creates an extra render, can loop when the
   dependency is the state it sets, and lets the rendered value lag one paint
   behind. **Derive during render instead**:
   `const fullName = first + ' ' + last;`. Effects are for syncing with
   something *outside* React (a subscription, a timer, the DOM) — not for
   computing values from existing props/state. Persisting through
   `useLocalStorage` is already a render-time read plus a write-on-change; it
   needs no effect around it.
3. **React Router API version mix-ups.** The starter is on React Router 7's
   **data router**. Mixing APIs breaks it: `createBrowserRouter` is paired
   with `<RouterProvider>` and a route-object array, **not** with
   `<Routes>`/`<Route>` JSX; `<BrowserRouter>` is a *different* (declarative)
   API and must not wrap a `RouterProvider`. `useRoutes` is a third. Pick the
   one the starter uses — `createBrowserRouter` + `RouterProvider` — and add
   routes to its array. In tests, use `createMemoryRouter` with the same array,
   not `<MemoryRouter>`.
4. **`localStorage` and serialization pitfalls.** `useLocalStorage` stores
   `JSON.stringify(value)`, so anything not JSON-serializable (a function, a
   `Date` becomes a string, a `Map`/`Set`, `undefined`) does not round-trip —
   the read side returns the fallback or a string, not the object you wrote.
   A malformed stored value falls back to `initial` rather than throwing (the
   hook catches it), so a corrupt key degrades gracefully instead of crashing —
   but do not rely on that to hide a typing bug. Also remember storage is
   per-origin and shared across tabs; treat it as a cache, not authoritative
   state.
5. **Route added but unreachable.** Creating only `src/pages/<Name>.tsx`
   without adding the entry to `src/App.tsx` leaves the page unrendered — the
   file exists, the build passes, and nothing routes to it. Add both the
   component and the route entry; add the nav link too if it should appear in
   the nav.

## SPA fallback

Only `/index.html` exists on disk after the build, so a static host must serve
`index.html` for any path that is not a real file, or a direct visit to
`/about` returns a 404. The starter ships `public/_redirects` with the
Cloudflare Pages rule (`/*  /index.html  200`); other hosts need the
equivalent (an nginx `try_files`, a rewrite to `/index.html`). This is a
deployment concern — the dev server and the in-app router already handle
client-side paths.

## Upgrade note

Starter version **1.1.0** (2026-10): the stack was bumped to **React 19**
(from 18), **React Router 7.18** (`react-router-dom`), **Vite 8**, **Vitest 4**
and **ESLint 10**. The React Router data-router API this skill documents
(`createBrowserRouter` + `<RouterProvider>` + a route-object array,
`createMemoryRouter` in tests) is unchanged in 7.18 — existing routes, links
and tests need no edits. Two things to know:

- **React 19**: the component and hook patterns here are unchanged, but React
  19 removed a few legacy APIs (e.g. `ReactDOM.render`, string refs). This
  starter's code does not use them. `@types/react` / `@types/react-dom` are on
  19; keep them in step with `react`/`react-dom`.
- **ESLint is now 10** with `eslint-plugin-react-hooks` v7 and
  `eslint-plugin-react-refresh` v0.5; the flat config in `eslint.config.mjs`
  is unchanged. **Vitest 4** keeps the `vitest run` script and
  `vitest.config.ts` shape.

When the starter version in `.sprout/starter.json` falls behind the embedded
tree, this section carries the upgrade note and the agent may propose — but
never silently apply — the upgrade; apply it only when the user explicitly
approves.
