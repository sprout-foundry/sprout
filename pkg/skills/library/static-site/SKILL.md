# Static Site Starter — Stack Knowledge

This project is an **Astro** static site (the `static-site` starter). Astro
renders every page to plain HTML at build time; the output in `dist/` is
static files with **no client-side JavaScript runtime** unless you opt in.
Work with that grain, not against it.

Commands come from `.sprout/starter.json` — never guess them:

```json
{ "build": "npm run build", "test": "npm test",
  "dev": "npm run dev", "format": "npm run format", "lint": "npm run lint" }
```

`npm run build` writes `dist/`; `npm test` runs vitest **against `dist/`**, so
build before you test.

## Layout — where things go

```
src/
  pages/            one .astro file per route; the file path IS the route
    index.astro       → /
    about.astro       → /about/   (a directory route: about/index.html)
  layouts/
    BaseLayout.astro  the shared HTML shell (head, header, nav, footer, <slot/>)
  components/
    ContactForm.astro a reusable component, imported by pages
  styles/
    global.css        global CSS, imported once by BaseLayout
  config.ts           site-wide config (CONTACT_ENDPOINT lives here)
public/               copied verbatim into dist/ (favicon.svg, 404.html)
test/                 vitest specs (*.test.ts)
design/               the design tree (tokens, screens, flows) — see its README
dist/                 build output (gitignored); never edit by hand
```

Rules of thumb:

- A **route** is a file under `src/pages/`. There is no separate router.
- **Shared markup** (header, nav, footer, `<head>`) lives in
  `src/layouts/BaseLayout.astro` — pages wrap their content in it.
- **Reusable UI** lives in `src/components/` and is imported where used.
- **Site-wide values** (an endpoint, a site name) belong in `src/config.ts`,
  exported as a named constant, and imported where needed. The contact form's
  `CONTACT_ENDPOINT` is the single place its external endpoint is set — change
  that one export to point the form at a different backend, never the URL
  inline in the component.
- **Static files served as-is** (favicon, `404.html`, images you don't want
  processed) go in `public/` and are referenced from the site root, e.g.
  `href="/favicon.svg"`.
- **Never edit `dist/`** — it is regenerated by `npm run build`.

## Adding a page

Create `src/pages/<name>.astro`. The file path becomes the route
(`src/pages/pricing.astro` → `/pricing/`). Import and wrap the shared layout:

```astro
---
import BaseLayout from '../layouts/BaseLayout.astro';
---

<BaseLayout title="Pricing">
  <h1>Pricing</h1>
  <p>Content goes here.</p>
</BaseLayout>
```

The `---` fenced block at the top is **frontmatter**: it runs at build time on
the server, never in the browser. Use it for imports and for computing values.
Everything below the fence is the template — HTML plus `{expression}`
interpolation of frontmatter values.

If the page is linked from the nav, add it to the `nav` array in
`BaseLayout.astro` so navigation stays consistent.

## Adding a component

Drop `src/components/<Name>.astro` and import it into a page (or another
component) with a **relative path**:

```astro
---
import { CONTACT_ENDPOINT } from '../config';
---

<section class="contact">
  <form method="post" action={CONTACT_ENDPOINT}>
    <input id="email" name="email" type="email" required />
    <button type="submit">Send</button>
  </form>
</section>
```

A component receives props via `Astro.props` — declare a `Props` interface in
the frontmatter and destructure it:

```astro
---
interface Props { title: string }
const { title } = Astro.props;
---
<h2>{title}</h2>
```

Props declared with `interface Props` are type-checked by `astro check`/tsc; a
prop a caller forgets to pass is a TypeScript error, not a silent `undefined`.

## Adding a test

Tests are vitest specs under `test/`. This starter tests the **built output**:
`test/home.test.ts` reads `dist/index.html` and asserts the rendered HTML (the
`<title>`, the `<h1>`, the about link, and the contact form's endpoint). The
pattern:

```ts
import { readFileSync } from 'node:fs';
import { fileURLToPath } from 'node:url';
import { describe, expect, it } from 'vitest';

const html = readFileSync(
  fileURLToPath(new URL('../dist/index.html', import.meta.url)),
  'utf8',
);

describe('built home page', () => {
  it('renders the heading', () => {
    expect(html).toMatch(/<h1[^>]*>Welcome<\/h1>/);
  });
});
```

To test a new page, add `test/<name>.test.ts` reading its built HTML
(`../dist/<name>/index.html`). **Build first** — the test reads `dist/`, and
vitest does not run the build for you (`npm run build && npm test`). A test
that reads `dist/` without a build fails on a missing file, which is expected,
not a bug in the test.

## Astro patterns to use

- **Frontmatter for data, template for markup.** Imports and computation go
  in the `---` block; the HTML body interpolates with `{}`.
- **`<slot />` for composition.** `BaseLayout` renders `<slot />` where page
  content goes; a layout or wrapper component passes children through it.
- **Relative imports for project modules** (`../config`,
  `../layouts/BaseLayout.astro`, `../components/ContactForm.astro`).
- **`public/` for verbatim assets**, referenced from the site root (`/…`).
- **Keep pages static.** Forms post to an external endpoint; that is the
  intended way this starter handles submission without a backend.

## Astro patterns to avoid

- **Do not add client-side JavaScript by default.** A `<script>` tag that
  manipulates the DOM, a framework island, or a `fetch`-on-load assumes a
  client runtime this static build does not provide. If you truly need
  interactivity, opt in deliberately (an Astro island with a hydration
  directive like `client:load`, or an explicit bundled `<script>`), and say so
  — do not assume a plain `<script>` runs like it would in a SPA.
- **Do not use a client-side router, `window`/`document` at module scope, or
  React/`useState` idioms.** There is no component runtime on the client; state
  is per-request build-time only.
- **Do not use absolute filesystem or alias imports that do not exist.** This
  starter has no path aliases configured — always relative paths from the file.
- **Do not put global site chrome in individual pages.** Put it in
  `BaseLayout` and wrap pages in it.
- **Do not edit `dist/` or commit it.** It is build output.
- **Do not hardcode the form endpoint** in the component — it comes from
  `CONTACT_ENDPOINT` in `src/config.ts`.

## Known failure modes for open models

These are the mistakes that recur on this stack — check for them before
declaring a change done:

1. **Client JS in static pages.** Writing a `<script>` that tries to run on
   load, or importing a framework component expecting it to be interactive.
   Astro strips/does not hydrate it unless you add a hydration directive; the
   page still builds and the test still passes, but nothing runs in the
   browser. If the feature needs the client, opt in explicitly with an island
   (`client:load` etc.); otherwise implement it at build time.
2. **Wrong import paths.** Pages live in `src/pages/`, so a layout import is
   `../layouts/BaseLayout.astro` and config is `../config` — **not**
   `./layouts/...` or an `@/` alias (none is configured). A wrong path fails
   the build with a module-not-found error; fix the relative path.
3. **`.astro` frontmatter mistakes.** The fence must be exactly `---` on its
   own line at the very top. Imports and `Astro.props` usage belong **inside**
   the frontmatter; a value defined there is available in the template via
   `{}` but is **not** exported to other files — export it from a `.ts`
   module (like `src/config.ts`) if another file needs it. Referencing a
   frontmatter variable outside `{}`, or a prop the caller never passed, gives
   `undefined` in the output (or a tsc error for a typed `Props`) rather than
   the intended value.
4. **Forgetting to build before testing.** `npm test` reads `dist/`; running
   it after editing source without `npm run build` tests stale (or missing)
   output. Always `npm run build` first.
5. **Assuming a router.** Adding a new page does not require a route entry —
   but if it should appear in navigation, add it to the `nav` array in
   `BaseLayout.astro`; otherwise it is reachable only by URL.

## Upgrade note

Starter version **1.1.0** (2026-10): the stack was bumped to **Astro 7** (from
5), **Vite 8**, **Vitest 4** and **ESLint 10**. The Astro conventions this
skill documents are unchanged — pages, layouts, components, `Astro.props`,
`<slot />` and the static-output `astro.config.mjs` all work the same in Astro
7, so existing pages and components need no edits. Two tooling changes matter
when you touch config or dependencies:

- **ESLint is now 10** and `eslint-plugin-astro` is on the v2 line, which
  requires ESLint 10 (its flat-config usage in `eslint.config.mjs` is
  unchanged). Do not downgrade `eslint` below 10 with this plugin version.
- **Vitest is now 4**; `vitest.config.mjs` and the `vitest run` script are
  unchanged, but a spec that relied on a Vitest 2-only option may need the
  current option name.

When the starter version in `.sprout/starter.json` falls behind the embedded
tree, this section carries the upgrade note and the agent may propose — but
never silently apply — the upgrade; apply it only when the user explicitly
approves.
